# Lifecycle checkpoints

Browser-testing reports are retained separately under `.pegatus/work/<task-id>/evidence/browser/`; they are not executable-command checks. The host coordinator preserves selected scenario outcomes and existing completion/security gates. A passing build cannot substitute for browser evidence. Native edit hooks do not prove browser actions or shared application data changes were observed; retain browser/deployment provenance and explicitly recheck affected scenarios after changes. See [browser testing](browser-testing.md).

`dispatchEvent(event,deps)` accepts an explicit absolute root, existing task ID, unique event ID and one of `session-start`, `before-action`, `post-edit`, `pre-compact`, `session-end`, or `complete`. It returns a Result. Only a completed state checkpoint records the event ID, so a failed save, reconciliation, or security gate can be retried. IDs and native session bindings are hashed in `progress.json`; no native tool input, output, transcript, credentials, or learning candidate body enters the lifecycle journal. The journal retains up to 4096 event IDs per task and then rejects new events; it never evicts old IDs and reexecutes a replay. Archive or roll over a completed task before reaching that limit.

Each new journal entry also stores a hash binding its ID to the event type and native session, plus the approved scope and action reference for `before-action`, or approved scope and explicit configuration file set for `complete`. Reusing an ID with different inputs blocks, even when the new inputs independently satisfy their gate. Legacy ID-only entries cannot satisfy required gates; use a new unique ID. Exact `before-action` replays must supply current reviewed evidence again, and exact `complete` replays reread repository state, validate current verification and rescan the explicit configuration files. A successful replay returns `skipped` without another checkpoint or learning collection; stale proof or changed unsafe configuration blocks.

Start reconciles the task's declared repositories and blocks dependent Pegatus work on discrepancies. Post-edit refreshes those repository snapshots. When source content changes or cannot be established, it marks prior verification and evidence `valid:false`, retaining their paths and earlier results for reporting. An unchanged file callback does not invalidate current proof. Pre-compaction and session end save the state and can call an injected optional `collectLearning` callback with task, hashed event reference and revision only. `before-action` needs an injected trusted authorization callback or the reviewed CLI record below; no host permission is invented. Completion requires a nonempty set of current valid checks with command evidence bound to repository content; each check must pass or have a specific reviewed limitation as described below. Explicit affected configuration files are also required. It calls `scanAgentConfig({root,files})` and only checkpoints completion after a valid `passed` scanner result. Changed application code still needs its separate review.

`repositoryCodeState(repos)` is the exported verifier/completion fingerprint. It hashes sorted repository IDs, source-content fingerprints and dirty-submodule uncertainty under the `repos-v1:` prefix; it deliberately excludes Git HEAD and the dirty boolean. Verifiers should pass `getCodeState: async () => repositoryCodeState(await currentRepositories(root, record))` and save the resulting aggregate with its check results and evidence. A later edit to an already dirty file changes the fingerprint and blocks completion; a commit without content changes retains the same verification state. Missing repositories or dirty submodules block completion. Existing verification dispositions and evidence remain intact; any accepted limitation must satisfy the specific check, scope, current evidence, and human-review bindings below.

Explicit calls work without native hook setup:

```text
node bin/pegatus.mjs lifecycle --root <explicit-root> --task <task-id> --event-id <unique-id> --type pre-compact
node bin/pegatus.mjs lifecycle --root <explicit-root> --task <task-id> --event-id <unique-id> --type complete --config-file <relative-config>
node bin/pegatus.mjs lifecycle --root <explicit-root> --task <task-id> --event-id <unique-id> --type before-action --action-ref <action-ref> --review-file <relative-review.json>
```

The CLI returns exit 0 for passed or a replayed checkpoint, 1 for failed, 2 for invalid usage, and 3 for blocked. A missing task blocks explicit `complete` and `before-action` calls; native callbacks for unbound or missing tasks skip. A `complete` call must repeat `--config-file` for every affected agent configuration file; missing scope blocks completion. Explicit calls are the gate for consequential workflow operations, including compaction when no unique native invocation ID is available.

The root-contained review file for `before-action` has this shape:

```json
{"schemaVersion":1,"kind":"action","status":"passed","taskId":"TASK-1","actionRef":"deploy:staging","scopeHash":null,"reviewedBy":"user","reviewedAt":"2026-10-13T00:00:00.000Z","evidenceRef":"chat:approval-1"}
```

`actionRef`, `taskId` and `scopeHash` must exactly match the pending action and saved task. The review is an explicit caller-supplied record of a separate user decision, with a reference to its evidence; it is not proof that the reviewer is who the file says, a host permission grant, or a substitute for host approval. A design approval alone never authorizes deployment or another external action. Missing, mismatched, malformed, or non-action review records block the Pegatus call. The `authorizeAction` API callback has the same reviewed-record contract and is the trusted coordinator's responsibility.

## Reviewed verification limitations

Completion may retain specific failed or blocked checks only when a trusted coordinator supplies `authorizeLimitations`, or the explicit CLI caller passes `--limitations-file <root-contained-review.json>` to `lifecycle --type complete`. This is a record of a separate human decision, not authentication of the reviewer or permission to bypass a host. Verification and every command evidence item must still be valid for the current repository code state. Scanner failures and security blockers cannot be accepted through this review.

```json
{"schemaVersion":1,"kind":"verification-limitations","taskId":"TASK-1","scopeHash":null,"codeState":"repos-v1:<current-content-digest>","reviewedBy":"human reviewer","reviewedAt":"2026-10-13T01:00:00.000Z","evidenceRef":"review/limitation.json","limitations":[{"checkId":"integration","status":"blocked","evidenceHash":"<sha256-of-JSON.stringify(check.evidence)>","reason":"Docker unavailable; this specific check is accepted for the reviewed scope"}]}
```

The review must cover exactly the outstanding checks and match task, approved scope, current code state, check status, and the SHA-256 of each check's entire evidence array. Changed evidence or scope requires a fresh review. Completion stores the reviewed limitations in its lifecycle journal and preserves each check's actual `failed`/`blocked` status. Replaying completion rechecks current verification, limitations authorization, and security; an old successful checkpoint cannot substitute for a current review. Required direct `before-action` and `complete` calls with an injected unbound `sessionId` block, even for a missing task. Advisory native callbacks retain their documented skip behavior.

## Native activation

`pegatus hook-activation --host claude|codex --root <installed-root>` prints a versioned JSON merge proposal; `doctor` includes the same proposal under `hookActivation`. Review and merge its `hooks` object into existing `.claude/settings.json` or `.codex/hooks.json` yourself. The installer does not alter existing host settings, register hooks, or claim active native enforcement. The command names only the fixed installed runtime and host. It never embeds task IDs, prompt text, file paths from tool input, or other task data in shell code. Roots with shell metacharacters cannot receive an automatic command proposal and must use explicit CLI calls.

Launch the host for one explicitly selected task with `PEGATUS_ROOT` set to that installed root and `PEGATUS_TASK_ID` set to its existing task ID. The `SessionStart` bridge records a hash of the native session ID under that task; later mapped events must have that binding. `PEGATUS_SESSION_ID` may additionally pin an already known native session ID. Missing task binding, unknown task records, mismatched session IDs, unsupported tool events, and Antigravity native events skip. Hook stdin never chooses the root or task. The bridge limits JSON input to 256 KiB and writes no raw payload. Replayed events across separate processes use the task's durable progress CAS.

The merge proposal covers documented `SessionStart`, file-edit `PostToolUse` (`Edit`, `Write`, `NotebookEdit` on Claude; `apply_patch` on Codex), and `SessionEnd`. Shell commands and arbitrary MCP tools cannot be proven to be edits from those events, so use an explicit `post-edit` call after they modify files. Native `PreCompact` is available to a manually configured hook only when a trusted wrapper supplies a distinct `PEGATUS_EVENT_ID` for each invocation. That variable is ignored for other native events, which use their own event/tool IDs. The default proposal leaves compaction to the explicit CLI; a fixed compaction ID would suppress later checkpoints. `complete` and `before-action` also remain explicit calls. Antigravity has no audited native hook registration, so it uses explicit calls.

Native responses follow each documented event rather than pretending all failures block. `PreCompact` can stop compaction: Claude receives exit 2 and Codex receives JSON `continue:false`. `PostToolUse` occurs after a tool ran and cannot undo an edit; the bridge returns advisory context. `SessionStart` and `SessionEnd` are also advisory. Codex local hooks have tool-path exceptions and may proceed after hook failures; these native integrations supplement, but do not replace, required Pegatus CLI gates. A manual merge needs a live host trust/acceptance check on Windows and Linux before marking a host's hooks `native` in doctor.

Host semantics: [Claude Code hooks reference](https://code.claude.com/docs/en/hooks), [Codex hooks reference](https://learn.chatgpt.com/docs/hooks). The audited compatibility limits are in [hosts.md](compatibility/hosts.md).
